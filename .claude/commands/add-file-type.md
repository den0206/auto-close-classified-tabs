# ファイル種別を追加する

タブの色分けに新しい拡張子・ドットファイル・色を追加する。
更新箇所が複数に分かれていて漏らしやすいので、**必ず全部を揃えて**変更する。

## 手順

### 1. 追加内容の確定

`$ARGUMENTS` を読み、次を決める。指示が曖昧なら決める前に確認する。

- 対象（拡張子 / ドットファイル / パスのパターン）
- **既存の色を使い回すか、新しい色 ID を足すか**
- 記号（`icon`）とバッジ（`badge`）

**既存の色で足りるなら新しい色を足さない。** 色は 26 で既に多く、橙系は複数の言語に割り当たっている。
色を増やすほど見分けにくくなるので、書式や役割が既存のどれかと同じなら使い回す。

### 2. 更新する場所

#### 色を使い回す場合 — `src/rules.ts` だけ

| 追加先 | 用途 |
|--------|------|
| `BY_SUFFIX` | 拡張子（`.kdl` のようにドットから書く）、または `Dockerfile` のような拡張子なしのファイル名（小文字で） |
| `BY_DOTFILE` | `.gitignore` のような、拡張子として解釈できないドットファイル |
| `GENERATED_SUFFIXES` | 自動生成物。拡張子より優先される |
| `TEST_MARKERS` / `TEST_DIRS` | テストファイルの判定 |

#### 新しい色 ID を足す場合 — 5 箇所すべて

| ファイル | 追加するもの |
|----------|-------------|
| `src/rules.ts` | `ColorId` の union と `COLOR_IDS` 配列の両方 |
| `package.json` | `contributes.colors` に `autoCloseClassifiedTabs.<id>`（`dark` と `light` の 2 色。`highContrast` は自動でフォールバックする） |
| `package.json` | `maxTabsByType` の `propertyNames.enum`（種別上限のキーとして書けるようにする） |
| `package.nls.json` | `color.<id>` の英語説明 |
| `package.nls.ja.json` | `color.<id>` の日本語説明 |

**この 5 つがずれていると `npm test` の整合性テストが落ちる。** 落ちたら足し忘れを疑う。

### 3. 色を選ぶときの指針

- **言語に公式カラーがあればそれに寄せる**（TS 青 / Python 黄 / Go 水色 / Rust 橙 / Ruby 赤）。見慣れた対応の方が覚え直さずに済む。
- **彩度を落としすぎない。** 非アクティブなタブは薄く描画されるので、彩度が低い色は無彩色に見える（`json` の初期値 `#B5CEA8` がこれで失敗した）。
- **隣接する色と色相をずらす。** 同じ用途で並びやすいもの（`json` / `yaml` / `toml` など）は、明度ではなく色相で分ける。
- `light` はテーマの背景が明るいので、`dark` より暗く濃い値にする。

### 4. 記号を選ぶときの指針

- **同じ色のものどうしは必ず違う記号にする。** 色が同じでも記号で見分けられるようにするのが記号の役目。
- フォント依存の珍しい文字を使わない（`🅙` は環境によって出ないので `{}` に置き換えた経緯がある）。
- 標準的な絵文字か、`{}` `<>` `#` のような ASCII 記号を使う。

### 5. テストの追加

`src/rules.test.ts` に、追加した種別のケースを足す。

- 拡張子 → 色 の対応（`cat('/a/foo.kdl')` が期待する色を返す）
- 既存の判定より優先される／されないの関係（テスト・自動生成・ドットファイルとの前後関係）
- 同じ色の他の種別と**記号が違う**こと

### 6. 検証

```bash
npm test   # 整合性テストを含む。ここが通れば 4 箇所の同期は取れている
```

`customLabels` のパターンを確認したい場合：

```bash
node -e "const {buildLabelPatterns}=require('./out/rules.js');console.log(buildLabelPatterns())"
```

### 7. ドキュメントの更新

色 ID を増やした場合のみ、次も更新する。

- `README.md` と `README_JP.md` の色の表
- `CHANGELOG.md` の `[Unreleased]`

拡張子を既存の色に足しただけなら、README の表に例として並んでいなければ更新は不要。

## 注意

- **色が実際にどう見えるかはテストでは分からない。** 色を足したら `F5` で起動して目視確認するようユーザーに伝える。
- タブに出るのは色と（`customLabels` を適用していれば）記号だけで、**バッジはタブに表示されない**。バッジは Explorer 用。
- 判定順は 差分 → テスト → 自動生成 → 拡張子 → ドットファイル。この順序を変える場合は既存テストへの影響を確認する。
