# マージ前レビュー（取り込み可否の判定）

現在の未コミット変更（またはブランチの差分）を**厳密にレビュー**し、マージの安全性とコード品質を担保する。

## 手順

### 1. 変更の把握

- `git status -s` と `git diff`（未追跡は該当ファイルを読む）で**変更内容をすべて把握**する。
- ブランチの差分を見る場合は `git log --oneline <base>..HEAD` と `git diff <base>...HEAD` を使う。
- 変更ファイル一覧と差分の概要を簡潔にまとめる。

### 2. 品質チェックの実行

以下を**必ず**実行する。

| チェック | コマンド | 合格基準 |
|----------|---------|----------|
| TypeScript 型チェック | `npm run typecheck` | エラー 0 |
| ユニットテスト | `npm test` | 全テスト合格 |
| 統合テスト | `npm run test:e2e` | 全テスト合格。VS Code を起動するため時間がかかる |
| VSIX 梱包 | `npm run package` | 成功し、`l10n/` と `package.nls.ja.json` が含まれる |

型チェックとユニットテストは独立しているので**並列に実行**してよい。
統合テストは差分が `src/e2e/` 以外に及ばない小さな変更なら省略してよいが、**省略したことを結果に明記**する。

### 3. 厳密レビュー観点

このプロジェクトは**ストレージ・メモリ・セキュリティを最優先**する方針で作られている。
以下を**必須**で確認する。

| 観点 | 確認内容 |
|------|----------|
| **ストレージ** | `globalState` / `workspaceState` / `secrets` を使っていないか。ファイル書き込みを追加していないか。設定への書き込みを増やす場合、**取り消すコマンドと必ずペア**になっているか。 |
| **メモリ** | 追加した `Disposable` が `context.subscriptions` に登録されているか。クロージャが `vscode.Tab` / `TextDocument` を保持していないか（破棄済みオブジェクトを生かしてしまう）。`setInterval` を持ち込んでいないか。`LruTracker` の `forget` / `retain` を通る経路が残っているか。 |
| **データ喪失防止** | `pickTabsToClose` の除外条件（`isDirty` / `isPinned` / `isActive` / グループ内で唯一のタブ）が壊れていないか。**未保存タブを閉じうる変更は無条件でブロッカー**。 |
| **依存** | `dependencies` が空のままか（実行時依存ゼロ）。新しい devDependency に妥当な理由があるか。 |
| **vscode 非依存の維持** | `src/rules.ts` と `src/autoClose.ts` が `vscode` を import していないか。ここが崩れるとユニットテストが動かなくなる。`grep -l "from 'vscode'" src/rules.ts src/autoClose.ts` が空であること。 |
| **l10n** | 新しい UI 文字列が `vscode.l10n.t()` 経由か（ソースに日本語のベタ書きが無いか）。manifest の新規文字列が `%key%` になっているか。英日の nls が揃っているか（`npm test` の整合性テストが見る）。 |
| **色・記号の整合** | `ColorId` / `contributes.colors` / `package.nls*.json` の 3 者が一致しているか（テストで検証済み）。新しい記号が既存の記号と重複していないか。 |
| **正規表現** | ユーザー入力を正規表現に通していないか（ReDoS 回避のため、意図的に単純な文字列マッチのみにしてある）。 |
| **保守性** | コメントが「何を」ではなく「なぜ」を書いているか。不要なコメントを増やしていないか。 |

### 4. レビュー結果の出力形式

以下の形式で**必ず**出力する。

```
## 変更概要
- （変更ファイルと役割の一行サマリ）

## 品質チェック
- TypeScript: （結果）
- ユニットテスト: （結果 — N テスト合格）
- 統合テスト: （結果、または省略した理由）
- VSIX 梱包: （結果 — サイズとファイル数）

## マージ安全性
- **ブロッカー（必須で直す）**: （あれば箇所と理由、なければ「なし」）
- **強く推奨（直すべき）**: （あれば箇所と理由、なければ「なし」）
- **任意の改善**: （あれば簡潔に、なければ「なし」）

## 判定
- **取り込み可** / **要修正のため取り込み不可**
```

### 5. 判定基準

- **ブロッカーが 1 つでもある**、または **品質チェックがエラー** → **取り込み不可**。
- 未保存タブを閉じうる変更、保存データを増やす変更、実行時依存の追加は**無条件でブロッカー**。
- ブロッカーがなく、強く推奨のみ → **取り込み可**（修正を推奨するがマージは許可）。
- ブロッカーも強く推奨もない → **取り込み可**。

### 6. 次のアクション選択

レビュー結果の出力後、**判定に応じた選択肢**を `AskUserQuestion` ツールで提示する。

#### 「取り込み可」の場合

| 選択肢 | 説明 |
|--------|------|
| **機能別にコミットを作成** | `/commit-by-feature` を実行して機能ごとにコミットする |
| **全変更を一括コミット** | すべての変更を 1 つのコミットにまとめる |
| **強く推奨の項目を先に修正** | 強く推奨がある場合のみ表示。指摘を修正してから再レビューする |
| **何もしない** | レビュー結果の確認のみで終了する |

#### 「取り込み不可」の場合

| 選択肢 | 説明 |
|--------|------|
| **ブロッカーを自動修正** | 指摘されたブロッカー（と強く推奨）を修正し、再度レビューを実行する |
| **何もしない（手動で直す）** | レビュー結果を参考に手動で修正する |

## 注意

- レビューは**コードの内容に基づいて**行う。推測で「多分大丈夫」にしない。
- **未保存ファイルを閉じないこと**と**データを保存しないこと**がこの拡張の存在理由なので、そこを最優先で見る。
- 色や記号が実際にタブへどう見えるかは自動テストでは分からない。見た目に関わる変更は「目視確認が必要」と明記する。
